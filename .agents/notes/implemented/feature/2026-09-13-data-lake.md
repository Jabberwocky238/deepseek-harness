# Agent Note: Multiple data lakes with directory-local maps

Status: implemented

English | [中文](2026-09-13-data-lake.zh.md)

## Problem

Agents need to navigate multiple disk or S3 datasets, locate each file's directory map, and preserve summaries of changes at every level. The existing storage hub owns structured application records, not a colocated inventory of external data roots.

## Decision

The [data-lake service](../../../../packages/storage/data-lake/README.md) manages multiple named lakes. Each lake owns exactly one root index and any number of nested directory maps. Maps contain direct children only and live with agent-authored summaries in each directory's reserved metadata folder. Source providers implement listings and metadata IO; the indexer consumes that interface and publishes the root index after maps are written.

Directory revisions include child revisions, so descendant changes invalidate ancestor summaries. Agents supply prose against an indexed revision; the indexer rejects stale writes and never generates a substitute summary. Model-facing consumers expose selected records through logged tool results rather than hidden model context.

## Alternatives considered

**One configured root per service.** A single service must expose several independent lakes to the same agent, so roots belong to named lake configurations.

**External metadata storage.** The requested ownership keeps maps and summaries inside their corresponding source directories, including S3 prefixes. The storage hub therefore does not own these records.

**Program-generated summaries.** File statistics cannot replace the requested agent interpretation of changes. Scans only identify changes and invalidate summaries.

## Consequences

Every lake has its own serialized mutation queue and independently selected disk or S3 provider. Colocation requires metadata write access to source roots. Full scans retain the catalog in memory; configuration bounds accepted entries. Old metadata remains, multiple processes are not coordinated, and metadata-only S3 prefixes remain navigable. Disk change detection uses size and modification time rather than reading every file's contents.

Focused disk tests cover hierarchy, physical map locations, summary invalidation, stale writes, failed scans, symlinks, and lake isolation. Loader tests exercise configured activation; an HTTP S3 fixture exercises SDK pagination, colocated writes, and summary reads. The [recorded Session](../../../../snapshots/session/data-lake-turn/snapshot.yml) discovers two lakes, scans and summarizes one, verifies the saved summary, and compares the complete final workspace while the other lake remains untouched. Local fals3y integration covers two isolated buckets, a 1001-object directory spanning S3 pages, nested maps, summary persistence, stale revisions, and object deletion without Docker or cloud credentials.
